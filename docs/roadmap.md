# 開発ロードマップ

## 現在地

kendo-keiko.comは、スクレイピングの技術検証段階から、自動取得と手動登録を組み合わせて掲載情報を継続的に増やせる段階まで進んでいる。

掲載イベント・掲載団体が増え、日付・地域・参加条件・団体・キーワードによる絞り込みも利用できるようになった。今後は、Instagramを通じて利用者・掲載団体との接点を作りながら、情報量が増えても人間が探しやすく、検索エンジンやAIクローラーも必要な情報へ辿れるサイト構造へ改善する。

現在の公開パイプラインは、次の2種類のイベントを統合する。

- DynamoDBに保存された自動取得イベント
- `data/manual_events.json`でGit管理する手動イベント

手動登録用CLI、イベント単位の参加条件・確認日、Step Functionsによる情報源単位の実行、監視通知まで整備済みである。

## 開発原則

- 大きな実装Issueは原則1件ずつ進める
- データ保全、利用者向け改善、情報追加を偏らせず交互に進める
- 自動化に固執せず、正確な情報を早く掲載できる方式を選ぶ
- 公式情報へのリンク、参加条件、最終確認日を保持する
- スクレイピング失敗や一時的な未検出で、既存イベントを即時削除しない
- 画面の機能を増やす前に、スマートフォンでの探しやすさを優先する
- 地図、アカウント、口コミなど運用負荷の大きい機能は後回しにする

## 優先順位

### 1. 利用者・掲載団体との接点を作る

Issue #49で「剣道稽古ナビ」のInstagram公式アカウントを開始する。

サイト内の情報を一方的に増やすだけでなく、実際の利用者や稽古会主催団体との接点を作る段階へ進む。

当面は次を行う。

- 稽古会情報や掲載団体を紹介する
- 剣道連盟、道場、剣友会、大学、社会人団体などをフォローする
- 掲載団体と自然な交流を行う
- 掲載希望・情報修正はInstagram DMでも受け付ける
- 実際にどのような情報が団体から提供されるかを観察する

掲載依頼フォームや団体管理画面を先に作り込まず、実際のやり取りから必要な入力項目と運用方法を確認する。

### 2. 掲載件数の増加に耐えるUIへ改善する

Issue #26を引き続き主要UI/UX Epicとして扱う。

日付・地域・参加条件・団体・キーワードによる絞り込みは実装済みであり、次の課題は掲載イベント・掲載団体の増加によるトップページの縦長化である。

Issue #74 では、情報量そのものを削減せず、人間がスマートフォンから探しやすい構成へ整理する。

主な検討対象は次の通り。

- トップページのイベント初期表示量
- 「もっと見る」などの段階的表示
- 日付単位のグルーピング
- 掲載団体セクションのコンパクト化
- 全イベント一覧ページの必要性
- 全掲載団体一覧ページの必要性
- スマートフォンでのスクロール量
- JS無効時の情報アクセシビリティ
- SEO・検索・AIクローラー向けの静的情報構造

イベント詳細ページや地域別ページを縦長化対策の前提にはしない。掲載できる詳細情報や地域ごとの掲載密度が十分になった段階で改めて判断する。

### 3. 関東の掲載密度を上げる

地域・民間団体のEpic #9と、剣道連盟のEpic #12を継続的に進める。

当面は埼玉、東京、神奈川、千葉を中心とし、「関東なら毎週どこかの稽古を見つけられる」状態を目指す。件数だけを追わず、公式情報を継続確認でき、外部参加条件を誤解なく掲載できる団体を優先する。

団体ごとに個別Issueを作り、自動、半自動、手動のうち運用負荷に合う方式を選択する。

情報追加は一度に大量に行わず、1団体追加するたびに次を確認する。

- 公式情報を継続して確認できるか
- 参加条件を誤解なく表現できるか
- 月次確認の負荷が許容範囲か
- 公開パイプラインとサイト表示が正常か

### 4. 再訪につながる便利機能

検索UXと基本的な一覧表示を維持しながら、実際の利用場面で便利な小さい機能を優先する。

当面は次の順で検討する。

1. Issue #11 のGoogleカレンダー追加
2. Issue #60 のLINE共有・URLコピー
3. Issue #10 の月間カレンダービュー
4. Issue #35 の静的イベント詳細ページ
5. Issue #59 の地域別一覧ページ

Googleカレンダー追加は、現在のイベントデータだけでも利用価値を提供しやすいため優先する。

共有機能はイベント固有URLの設計と合わせて検討する。イベント詳細ページは、カード以上の情報を十分に提供できる状態になった段階で優先度を上げる。

地域別ページも、地域ごとの掲載情報が十分な密度になった段階で優先度を上げる。

### 5. 団体から情報が集まる仕組みを作る

Issue #36では、掲載依頼・情報修正を団体側から受け付けられる導線を段階的に整備する。

最初から団体アカウントや管理画面を構築せず、次の順で進める。

1. Instagram DMで掲載依頼・修正依頼を受ける
2. 実際の依頼内容から必要項目を整理する
3. 掲載依頼フォームを追加する
4. 管理者確認後に公開できる流れを整える
5. 十分な需要が確認できた場合に団体自身による管理機能を検討する

団体ログイン、セルフサービスのイベントCRUD、権限管理などは現時点では対象外とする。

### 6. 差分反映と掲載状態の安全管理

Issue #25では、取得元から消えたイベント、変更されたイベント、一時的に取得できなかったイベントを安全に扱う。

Issue #21で情報源単位の失敗分離、Retry、警告・失敗記録、アラート通知までは整備済みである。また、現在は取得できなかったイベントを即削除する実装ではなく、古い未来イベントが残る側に倒している。

そのため、#25は重要だが現時点の最優先にはしない。掲載件数・更新頻度・団体数がさらに増え、古い未来イベントの確認負荷や月次確認負荷が目立ち始めた場合に優先度を引き上げる。

## 情報追加の運用負荷

- 手動掲載団体は月1回程度を目安に再確認する
- 月次確認が合計60〜90分以内なら手動掲載を継続する
- 月2時間を超えたら新しい手動団体の追加を一旦止める
- 運用負荷が増えた段階で、主催者投稿、半自動化、管理画面、収益化を再検討する

## 本番確認の基準

公開イベント総数は、開催日経過や取得元の更新によって変動するため固定値で判定しない。

定期取得後は次を確認する。

- Step Functionsの実行が成功している
- 情報源ごとの成功・警告・失敗件数が妥当である

手動イベントの単独公開後は、Publisherの `publish_only` 応答とS3原本を確認する。いずれの場合も次を確認する。

- 追加対象団体のイベントが期待件数公開されている
- 団体別件数に不自然な増減がない
- 必須メタデータの欠損が0件である
- 公式URL、参加条件、確認日が表示用JSONに含まれる

## 完了済みの主要基盤

- S3 + CloudFrontによる静的サイト公開
- 独自ドメインと基本SEO
- レスポンシブな剣道向けデザイン
- 全日本剣道連盟、東京都剣道連盟、神奈川県剣道連盟などの自動取得
- Step Functionsによる情報源単位の定期実行
- CloudWatch AlarmとSNS通知
- イベント単位の取得方式・参加条件・確認日
- 日付・地域・参加条件・団体・キーワードによる絞り込み
- 管理者CLIによる手動イベント管理
- 眞心会の手動掲載
- 手動団体追加から本番公開までの標準手順
- Publisherだけを更新する手動イベントの1コマンド公開
- サイト名「剣道稽古ナビ」、favicon、OGPなどのブランド整備
